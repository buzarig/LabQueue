Ось додаткова інформація по лабораторній роботі 2 


Мета: реалізувати основні сценарії спершу на статичних даних, потім замінити реальною роботою з БД.

Що зробити:
• spec.md: сценарії та очікувана поведінка; схема БД, запити, сценарії помилок.
• Прототип на статичних даних (без БД): основні сценарії через зовнішній інтерфейс — HTTP API (або UI-виклики). API покриває ВСІ основні сценарії, а не один GET; схема БД без API прототипом не вважається.
• Інтеграція БД: замінити статику реальною БД; транзакції, валідація, обробка збоїв джерела, ідемпотентність/ретраї.
• Рівні декомпозиції: роути знають про HTTP; сервіси — про бізнес-операції й доступи; SQL і транзакції — лише в репозиторіях/DAO. SQL чи транзакції в роутах — порушення меж.
• Керування залежностями: без протягування 10–15 параметрів. Щонайменше: ініціалізовані ресурси (БД), користувач-ініціатор, business-process ID, що автоматично потрапляє в кожен лог з будь-якого рівня. Варіанти: DI, context-реєстр, AsyncLocalStorage / contextvars, Effect тощо — вибір в ADR.
• Обробка помилок: один глобальний обробник, а не try/catch на все тіло кожної функції.
• Аудит: топ-3 зрізані кути / крайові випадки; N+1 (де виникла і як виправлено); поведінка на збоях.
• DEFENSE.md + adr/ на вибір БД/ORM і керування залежностями.

Рекомендації: пул БД — явна ініціалізація на старті + SELECT now() (падати одразу); ізольоване локальне середовище (не 5432/5433/5434 на localhost; окрема база на прогін/гілку); одна стратегія розміщення моделей; SQL tagged templates для сирого SQL.

Ознаки відмінного виконання: сценарії працюють через API спершу на статиці, потім на БД; шари не змішані; залежності й business-process ID без протягування параметрів; один глобальний обробник помилок; немає очевидних N+1; рішення захищені.

Якщо з AI: AI не є джерелом вимог і рішень — йому ставиться задача аналізу й дозбору (знайти прогалини, поставити уточнювальні питання, запропонувати варіанти), а формулює й вирішує студент; spec.md і DEFENSE.md — власноруч (DoD §1).
