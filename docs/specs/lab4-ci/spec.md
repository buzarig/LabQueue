# spec: Лаба 4 - CI/CD і розгортання LabQueue

## Що і навіщо

Хочу щоб у `main` потрапляли тільки зміни, які пройшли перевірки. Після зеленого CI для коміту в `main` Railway має автоматично оновити публічний staging. Поки нова версія запускається і проходить перевірку, запити ще йдуть на стару.

Правила черги описані в `docs/specs/lab1-foundation/architecture.md`. Правила роботи з ШІ є в `standards/ai-workflow.md`.

## Обсяг

Розгортаю лише staging. Поведінка API без змін. Майбутній prod матиме ті самі команди з образу й порядок міграцій. Малий PR із CD можна злити до ревʼю викладача для доказу автодеплою. Правила мерджу діють і для нього.

## Критерії прийняття

| № | Критерій | Перевірка |
|---|---|---|
| **A** | **CI і мердж** | |
| 1 | GitHub Actions запускає `make check` на PR і push: формат, лінт, типи, межі модулів, тести, збірка, smoke, Conventional Commits і гігієна | `check.yml`, `Makefile` |
| 2 | Зміни входять у `main` через PR із зеленим чеком `check` і лише через merge commit | правила GitHub, аудит PR |
| 3 | CI використовує окремий PostgreSQL 17. Доступу до БД staging/prod і SSH для деплою немає | рев’ю workflow й налаштувань |
| **B** | **CD** | |
| 4 | Railway із Wait for CI після зеленого CI збирає образ із коміту в `main` і розгортає його на staging із PostgreSQL 17 на Railway | логи CI і CD, `SHOW server_version` |
| 5 | Публічний `GET /version` повертає SHA коміту з деплою | HTTP-запит, лог CD |
| 6 | Railway перемикає трафік після HTTP 200 від `/ready` нової версії з підключеною PostgreSQL | лог CD, HTTP-запити під час деплою |
| **C** | **Міграції** | |
| 7 | Структурні міграції стартують в окремому контейнері з образом застосунку через Railway Pre-deploy, до запуску HTTP-контейнера | налаштування й лог CD, ADR |
| 8 | Структурні зміни сумісні зі старою версією. Видаляю старе окремим релізом, коли попередня версія вже обходиться без цих полів чи таблиць | рев’ю SQL і ручний сценарій читання й запису на старій версії після міграції |
| 9 | Фонова міграція пакетами до 100 рядків ставить `room = btrim(room)` у всіх заняттях із `room <> btrim(room)`. На staging до деплою створюю через API заняття з `room = "  101  "` | лог пакетів, `room` після міграції дорівнює `"101"`, HTTP під час прогону |
| 10 | Індекс `queue.entries (session_id, finished_at DESC)` для `passed` і `rework` створюється у фоні через `CREATE INDEX CONCURRENTLY` поза транзакцією | рев’ю SQL, лог кроку |
| 11 | Seed іде окремим кроком перед запуском HTTP лише з `SEED_ON_START=1` на staging. Типово вимкнений, повтор без дублів | два прогони з прапорцем і один без |
| 12 | Структура, дані й індекси лежать в окремих теках. Базова `migrations/001-schema.sql` збережена | дерево файлів, git diff |
| **D** | **Аудит і здача** | |
| 13 | Для шести порушень (формат, лінт, типи, тест, збірка, повідомлення коміту) є окремі PR із червоним прогоном потрібної перевірки й заблокованим merge | `reports/lab4/` |
| 14 | Збережено доказ автодеплою з `main`. Вибір інструментів і запуск Pre-deploy описано в ADR, підсумок записано в DEFENSE | `reports/lab4/`, `docs/adr/`, `DEFENSE.md` |
