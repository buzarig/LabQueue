# spec: Лаба 1 — фундамент і структура LabQueue

## Проблема і рішення

Черга на здачу лабораторних зараз живе в чаті групи: хтось займає місце й не
приходить, викладач не знає, скільки людей ще чекає, а студент — чи встигне
сьогодні. **LabQueue** — електронна черга на кожне заняття: одна прозора
послідовність, чесні правила пропуску й історія здач.

Мета лаби 1 — не функціонал, а фундамент: стандарти, конвеєр перевірок і
архітектура, виведена з поведінки черги та її даних, а не з вибраного
фреймворку. Функціонал продукту й правила черги описані в обов'язковому
додатку [architecture.md](architecture.md) (sf-1). Журнал змін spec —
[spec-fix.md](spec-fix.md).

## Межі лаби

**Робимо:**
- README з ідеєю;
- пакети, стиль коду, форматер, лінтер, статичний аналіз;
- перевірки перед комітом і пушем;
- CI (sf-3);
- smoke-тест;
- стандарти, архітектура, ADR;
- каркас модулів без логіки;
- аудит і DEFENSE.

**Не робимо:**
- логіку черги;
- БД;
- автентифікацію (ідентичність поки через заголовок);
- UI і живі оновлення;
- деплой (sf-3).

## Критерії прийняття

Стовпець «Перевірка» каже, чим саме доводиться критерій (sf-10).

| № | Критерій | Перевірка |
|---|---|---|
| **A** | **Спершу думаємо** | |
| 1 | `standards/` містить: формат spec, шаблон ADR (MADR), мій DoD, реєстр перевірок (що, якою командою, на якому етапі, що блокує), правила роботи з ШІ, конвенцію комітів | `ls standards/` + рев'ю змісту |
| 2 | `architecture.md` описує: функціонал і правила черги (sf-1); модулі, їх відповідальність і обґрунтування меж; дозволені напрями залежностей; ER; стани запису й заняття (sf-8); для кожного сценарію — які дані змінюються і які інваріанти мають втриматись | рев'ю за переліком розділів |
| 3 | ADR на кожне рішення з реальними альтернативами або дороге для зміни. Мінімум (sf-9): кожен інструмент (2–3 альтернативи); контроль меж модулів; модель позицій і захист від гонки; лічильник неявок; історія як запит у `queue`; spec + додаток architecture.md | `ls docs/adr/`, у кожному ADR — розділ альтернатив |
| 4 | Коміти стандартів, архітектури й ADR в історії раніше за перший коміт коду | `git log --reverse -- standards docs` раніше за `git log --reverse -- package.json src` |
| **B** | **Конвеєр** | |
| 5 | На свіжому клоні одна команда `make check` сама ставить пакети, якщо їх немає або lockfile новіший, і запускає формат, лінт, статичний аналіз, межі, збірку й smoke-тест — усе зелене, у файли нічого не пише (sf-4). Кроки описані в README. Той самий `make check` запускає CI на push і PR (sf-3) | `git clone … && make check` → код 0, `git status` чистий; зелений прогін CI на PR |
| 6 | Hook-и встановлюються автоматично разом із залежностями | після `npm ci` коміт запускає hook |
| 7 | Коміт з порушенням стилю/лінту відхиляється, пуш зі зламаною збіркою чи smoke-тестом — теж. Справжній вивід обох відмов лежить у `reports/lab1/` | `make verify` перегенеровує звіти (sf-5) |
| 8 | Застосунок стартує, відповідає на перевірку стану та `/version` з sha поточного коміту; без git — `unknown`, а не падіння | smoke-тест у `make check` |
| **C** | **Структура** | |
| 9 | Кожен модуль з `architecture.md` — окрема папка з однією публічною точкою входу; інших доменних модулів немає | правила dependency-cruiser у `make check` |
| 10 | Імпорт в обхід точки входу, цикл або заборонений напрям залежності валить `make check`. Демонстрація збережена у звіті | `make verify` → `reports/lab1/` (sf-5) |
| **D** | **Репозиторій і здача** | |
| 11 | Немає `node_modules`, артефактів збірки, секретів, випадкових файлів | `git ls-files` + `.gitignore`, рев'ю |
| 12 | Кожен промпт — дослівно в `ai/lab1/`. Кожен коміт ШІ має трейлер `Prompt: ai/lab1/NNN-назва.md`. Коміти прийняття — `docs: прийнято …` без трейлера (sf-6) | скрипт перевірки історії гілки |
| 13 | Аудит (`docs/audit/lab1.md`): статус кожного критерію з доказом; топ-3 зайві або неправильні залежності з рішенням; топ-3 «зрізані кути» ШІ: промпт → мій фідбек → зміна spec/стандарту → коміт | рев'ю, посилання на коміти |
| 14 | `DEFENSE.md` у корені за шаблоном курсу, ≤ 1 сторінки (sf-2). Вказує sha вершини feature-гілки, на якій пройшов `make verify` (sf-7) | рев'ю; `git merge-base --is-ancestor <sha> main` |
| 15 | feature-branch → PR з коментарями → звичайний merge, не squash (sf-7); один логічний крок на коміт | сторінка PR, `git log --graph` |

## Правила співпраці з ШІ

- **Прийняття чернеток.** ШІ пише чернетку spec, стандарту чи ADR, я приймаю
  її своїм комітом `docs: прийнято …`.
- **Зміни spec.** ШІ не править spec.md самостійно: кожна зміна проходить через
  [spec-fix.md](spec-fix.md) (sf-11).
- **Розбіжність зі spec** лікуємо зміною spec/стандарту (spec-fix), а не тихим
  патчем коду.
- **Залежності.** Кожна залежність має в README один рядок «навіщо».
- **Неоднозначність у spec** → ШІ зупиняється й питає.
