# spec: Лаба 1 — фундамент і структура LabQueue

## Проблема і рішення

Черга на здачу лабораторних зараз живе в чаті групи: хтось пише «я за Петром»,
хтось займає місце й не приходить, викладач не знає, скільки людей ще чекає,
а студент — чи встигне сьогодні. **LabQueue** — електронна черга на кожне
заняття: одна прозора послідовність, чесні правила пропуску й історія здач.

Мета лаби 1 — не функціонал, а фундамент: стандарти, конвеєр перевірок і
архітектура, виведена з поведінки черги та її даних, а не з вибраного фреймворку.

## Що вміє продукт (вхід для архітектури)

Реалізація — з лаби 2. Тут перелік потрібен, щоб з нього вивести модулі й дані.

**Викладач**
- Створює заняття: предмет, група, дата й час, аудиторія, ліміт черги,
  які лаби приймаються.
- Відкриває й закриває запис у чергу; завершує заняття.
- Викликає наступного студента.
- Фіксує результат здачі: «зараховано» (з балом) або «на доопрацювання».
- Позначає, що студент не підійшов.

**Студент**
- Бачить заняття своєї групи й стан їхніх черг.
- Стає в чергу з конкретною лабою; бачить свою позицію й орієнтовний час.
- Виходить із черги.
- Переглядає історію своїх здач.

**Правила черги**
- Один студент — щонайбільше один активний запис на заняття.
- Нові записи стають у кінець; позиції завжди йдуть підряд, без дірок.
- Неявка: перший раз — запис переходить у кінець черги, другий — вибуває.
- Запис неможливий, коли черга закрита, ліміт вичерпано або лаба не приймається.
- Керує заняттям лише викладач, що його створив.
- Статуси запису: `очікує → здає → зараховано | доопрацювання`;
  з `очікує` також `вийшов` і `пропуск`.

## Межі лаби

**Робимо:** README з ідеєю; пакети, стиль коду, форматер, лінтер, статичний
аналіз; перевірки перед комітом і пушем; smoke-тест; стандарти; архітектура;
ADR; каркас модулів без логіки; аудит; DEFENSE.

**Не робимо:** логіку черги, БД, автентифікацію (ідентичність поки через
заголовок), UI, живі оновлення, CI, деплой.

## Критерії прийняття

Кожен критерій доводиться командою, файлом або git-історією.

**A. Спершу думаємо**
1. `standards/` містить: формат spec, шаблон ADR (MADR), мій DoD, реєстр перевірок
   (що, якою командою, на якому етапі, що блокує), правила роботи з ШІ,
   конвенцію комітів.
2. `architecture.md` поруч зі spec описує: модулі, їх відповідальність і
   обґрунтування меж; дозволені напрями залежностей; ER-діаграму; діаграму
   станів запису в черзі; для **кожного** сценарію з розділу вище — які дані
   змінюються і які інваріанти мають втриматись.
3. Кожне рішення з реальними альтернативами або дороге для зміни — ADR.
   Мінімум: кожен інструмент/технологія, спосіб контролю меж модулів,
   модель позицій у черзі.
4. Коміти стандартів, архітектури й ADR в історії раніше за перший коміт коду.

**B. Конвеєр**
5. На свіжому клоні одна команда `make check` запускає формат, лінт, статичний
   аналіз, перевірку меж, збірку й smoke-тест — і все зелене. Кроки описані в README.
6. Hook-и встановлюються автоматично разом із залежностями.
7. Коміт з порушенням стилю/лінту відхиляється, пуш зі зламаною збіркою чи
   smoke-тестом — теж. Справжній вивід обох відмов лежить у `reports/lab1/`
   і відтворюється командою `make`.
8. Застосунок стартує, відповідає на перевірку стану та `/version` з sha
   поточного коміту; без git — значення `unknown`, а не падіння.

**C. Структура**
9. Кожен модуль з `architecture.md` = окрема папка з однією публічною точкою
   входу; інших доменних модулів немає.
10. Імпорт у обхід точки входу, цикл або заборонений напрям залежності валить
    `make check`. Демонстрація збережена у звіті.

**D. Репозиторій і здача**
11. Немає `node_modules`, артефактів збірки, секретів, випадкових файлів.
12. Кожен промпт — дослівно в `ai/lab1/`; кожен коміт за промптом має трейлер
    з посиланням на нього.
13. Аудит (`docs/audit/lab1.md`): статус кожного критерію з доказом; топ-3 зайві
    або неправильні залежності з рішенням; топ-3 «зрізані кути» ШІ — промпт →
    мій фідбек → зміна spec/стандарту → коміт.
14. `docs/defense/lab1.md` за шаблоном курсу, ≤ 1 сторінки.
15. feature-branch → PR з коментарями → merge; один логічний крок на коміт.

## Правила співпраці з ШІ

- ШІ пише чернетку spec/стандарту/ADR — я приймаю окремим комітом. Після
  прийняття ШІ змінює їх лише за моїм промптом.
- Розбіжність зі spec лікуємо зміною spec/стандарту (spec-fix), а не тихим
  патчем коду.
- Кожна залежність має в README один рядок «навіщо».
- Неоднозначність у spec → ШІ зупиняється й питає.
