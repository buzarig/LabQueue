# ADR-0038: Vitest як другий раннер — лише для `transitions.js`

- Статус: прийнято
- Дата: 2026-11-18
- Промпт: ai/lab3/003-vidpovidi-pro-testy.md, ai/lab3/004-vidpovidi-transitions-make-test.md, ai/lab3/012-tak-adr-instrumenty.md

## Контекст і проблема

Spec лаби 3 (критерії 4, 13) вимагає мутаційного тестування
`transitions.js` ([ADR-0037](0037-chysta-mashyna-staniv-transitions.md)).
Решта тестів проєкту написана на `node:test`
([ADR-0010](0010-node-test.md)). Stryker, обраний для мутацій
([ADR-0040](0040-stryker-mutatsii-transitions.md)), не має раннера для
`node:test`. Тому треба вирішити, на чому писати тести модуля, який
мутуємо.

## Чинники рішення

- **Stryker має розуміти раннер**: знати, який тест покриває мутанта
  (`coverageAnalysis: perTest`), і не проганяти всі тести на кожного.
- **Мінімум змін у наявних тестах**: усі тести на `node:test` лишаються
  як є (рішення автора, промпт 003).
- **Нативний ESM без збірки**, як решта проєкту.

## Розглянуті варіанти

1. **Vitest 5 лише для `transitions.js`**, решта на `node:test`.
2. **Stryker з `command`-раннером** поверх `node --test`.
3. **Перевести всі unit-тести на Vitest.**

## Рішення

Обрано **варіант 1** (рішення автора, промпти 003 і 004): це найменша
зміна, з якою Stryker працює повноцінно.

- Пакет `vitest`, основна версія **5** (`^5.1.0`). 5.1.1 вийшла в день
  рішення, тому в lockfile — 5.1.0.
- Тести Vitest лежать у `tests/vitest/`, окремо від `tests/unit/`. Тоді
  `node --test "tests/unit/**/*.test.js"` їх не підхоплює, а Vitest не
  бачить тестів `node:test`. Межа видна з шляху.
- Конфіг `vitest.config.js`: `include: ["tests/vitest/**/*.test.js"]`,
  `pool: "threads"`. Пул `threads` потрібен c8
  ([ADR-0039](0039-c8-pokryttia.md)): на типовому `forks` c8 бачить 0 %.
- Запуск — у складі `make test-unit` разом з `node --test`.

### Наслідки

- **Добре:**
  - Stryker знає покриття на тест і проганяє лише потрібні тести;
  - наявні тести не змінюються;
  - API `expect` і `test` знайомі й читаються без контексту.
- **Погано / ціна:**
  - два раннери в одному проєкті: два стилі тестів і два місця для
    налаштувань;
  - Vitest тягне Vite з транзитивними залежностями (`npm audit`: нові
    знахідки середнього й високого рівня в `picomatch` і `vite`, усі лише в
    devDependencies);
  - пул `threads` — умова для c8, а не вибір за швидкістю.

## Плюси й мінуси варіантів

### Варіант 2: `command`-раннер

- Плюс: жодного нового раннера, тести на `node:test`.
- Мінус: Stryker не знає, який тест покриває мутанта, і на кожного
  проганяє всю команду. Для ~90 мутантів це в десятки разів повільніше, а
  статус «no coverage» не розрізняється → відкинуто.

### Варіант 3: усі unit-тести на Vitest

- Плюс: один раннер для unit-рівня.
- Мінус: переписати 85 тестів, які не стосуються лаби 3. Spec (розділ
  «Обсяг») прямо обмежує зміни → відкинуто.
