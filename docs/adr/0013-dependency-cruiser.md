# ADR-0013: Контроль меж модулів — dependency-cruiser

- Статус: запропоновано
- Дата: 2026-09-30
- Промпт: ai/lab1/010-adr-stack.md

## Контекст і проблема

К9 і К10 вимагають, щоб порушення меж валило `make check` (CHK-04):
- імпорт в обхід `index.js`;
- цикл;
- заборонений напрям залежності.

Правила задані в [architecture.md](../specs/lab1-foundation/architecture.md),
розділ «Напрями залежностей»: матриця дозволених напрямів і 6 заборон.
Потрібен інструмент, який перевіряє їх автоматично.

## Чинники рішення

- **Покриття всіх трьох класів порушень**: обхід точки входу, цикли, напрями
  за матрицею.
- **Декларативні правила**, які читаються поруч із матрицею в architecture.md.
- **Зрозумілий звіт** для демонстрації в `reports/lab1/` (К10, CHK-11).
- **Розуміння ESM** і відносних імпортів без збірки.

## Розглянуті варіанти

1. **dependency-cruiser** — окремий аналізатор графа залежностей з
   правилами `forbidden`.
2. **ESLint `no-restricted-imports` / `import/no-restricted-paths`** —
   правила імпортів у лінтері.
3. **eslint-plugin-boundaries** — плагін ESLint, що описує елементи
   архітектури й дозволені зв'язки між ними.
4. **Власний скрипт** — розбір `import` регулярними виразами й перевірка за
   матрицею.

## Рішення

Обрано **dependency-cruiser**. Конфігурація `.dependency-cruiser.cjs`
перекладає правила з architecture.md так:

| Правило з architecture.md | Правило dependency-cruiser |
|---|---|
| 1. Обхід `index.js` | `forbidden`: з `src/modules/A/**` у `src/modules/B/**`, крім `src/modules/B/index.js` |
| 2. Цикли | `no-circular` |
| 3. Напрям поза матрицею | `forbidden` для кожної пари модулів, якої немає в таблиці |
| 4. Домен → `platform` / `main.js` | `forbidden`: з `src/modules/**` у `src/platform/**` і `src/main.js` |
| 5. `platform` → домен | `forbidden`: з `src/platform/**` у `src/modules/**` |
| 6. Спільні дані | не виражається імпортами. Перевіряється через правило 1 (чужі внутрішні файли недоступні) + рев'ю |

Кожне правило в конфігурації має коментар з номером правила в architecture.md.

### Наслідки

- **Добре:**
  - один інструмент покриває всі три класи порушень;
  - правила декларативні, тож їх можна звірити з матрицею рядок за рядком;
  - вивід придатний для звіту в `reports/lab1/`;
  - уміє будувати графи, що корисно для аудиту.
- **Погано / ціна:**
  - ще одна залежність розробки зі своїм синтаксисом конфігурації;
  - правила на рівні модулів, а не функцій, тож обмеження з
    [ADR-0005](0005-koordynatsiia-zavershennia-zaniattia.md) (перехід
    «завершене» лише з `queue`) він не перевіряє. Це вже записано як
    кандидат в аудит.

## Плюси й мінуси варіантів

### ESLint `no-restricted-imports` / `import/no-restricted-paths`

- Плюс: без нового інструмента, помилки видно в редакторі.
- Мінус: циклів не бачить (`import/no-cycle` — окреме повільне правило з
  плагіна). Матрицю напрямів доводиться переписувати як набір заборонених
  шляхів, які важко звіряти з таблицею → відкинуто.

### eslint-plugin-boundaries

- Плюс: мислить поняттями «елемент архітектури» й «дозволений зв'язок» — це
  найближче до матриці; помилки видно в редакторі.
- Мінус: цикли не покриває (знову потрібен `import/no-cycle`). Прив'язує
  контроль меж до ESLint, тож його аудит і заміна змішуються з лінтером.
  Реальна альтернатива, відкинута через цикли.

### Власний скрипт

- Плюс: нуль залежностей, правила пишемо як хочемо.
- Мінус: розбір імпортів регулярними виразами ламається на динамічних
  імпортах, коментарях і ре-експортах. Виявлення циклів довелося б писати й
  тестувати самим. Перевірка меж — центральний критерій лаби, тож тримати її
  на саморобному парсері ризиковано → відкинуто.
