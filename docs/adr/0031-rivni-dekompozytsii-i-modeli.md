# ADR-0031: Рівні декомпозиції, моделі й один глобальний обробник помилок

- Статус: прийнято
- Дата: 2026-10-23
- Промпт: ai/lab2/023-dodatkovi-vymohy-laby-2.md, ai/lab2/025-vidpovid-fail-fast-data-modeli-adr-0021.md

## Контекст і проблема

Курс вимагає (промпт 023):
- роути знають лише про HTTP;
- сервіси — про бізнес-операції й доступи;
- SQL і транзакції живуть лише в репозиторіях;
- одна стратегія розміщення моделей;
- один глобальний обробник помилок замість try/catch у кожній функції.

Лаба 1 задала межі між модулями, але не всередині модуля. Правило 7 лише
каже, що `fastify` дозволений тільки в `index.js` і `routes.js`.

## Чинники рішення

- **Межа видна з імені файлу** і перевіряється автоматично (правило «нове
  правило — з перевіркою», `standards/README.md`).
- **Модулі не імпортують `platform`** (правило 5 лаби 1).
- **Однаково для статики й БД** ([ADR-0027](0027-statyka-yak-druhyi-adapter.md)).

## Розглянуті варіанти

1. **Ролі файлів у модулі з правилами dependency-cruiser і ESLint;
   `model.js` у кожному модулі; помилки модуля в `errors.js`, глобальний
   обробник розпізнає їх за формою.**
2. **Папки-шари на весь застосунок** (`src/routes`, `src/services`,
   `src/repositories`, `src/models`).
3. **Спільне ядро `src/shared/`** з базовим класом помилки й типами, яке
   можуть імпортувати всі модулі.

## Рішення

Обрано **варіант 1**; розміщення моделей — промпт 025.

**Файли модуля** `src/modules/<м>/`:

| Файл | Знає про | Може імпортувати |
|---|---|---|
| `index.js` | збирає модуль, Fastify-плагін | усі файли свого модуля, `index.js` інших модулів |
| `routes.js` | HTTP: схеми, коди, заголовки | `service.js`, `model.js`, `errors.js` |
| `service.js` | бізнес-операції, доступи, інваріанти | `repo.js`, `model.js`, `errors.js`, API інших модулів |
| `repo.js` | контракт репозиторію (JSDoc) | `model.js` |
| `repo-memory.js`, `repo-pg.js` | дані; SQL лише в `repo-pg.js` | `repo.js`, `model.js`, `errors.js` |
| `model.js` | типи сутностей і статусів модуля | — |
| `errors.js` | коди помилок модуля | — |

Мапінг рядок ↔ модель — лише в `repo-pg.js`.

**Помилки.**
- Сервіс кидає помилку з `errors.js`: `{ code, statusCode, message }`.
- Один обробник `setErrorHandler` у `platform` розпізнає помилку за формою
  і відповідає `{ error: { code, message } }`.
- Помилки валідації Fastify → 400 `VALIDATION_FAILED`. Решта → 500
  `INTERNAL` із processId у лозі.
- `try/catch` дозволений лише в `platform/` (транзакції, ретраї) і в
  `repo-pg.js` (переклад SQLSTATE у помилки модуля).

**Перевірки** (у `make check`):
- dependency-cruiser: таблиця вище — правила `layer-*`;
- ESLint `no-restricted-syntax`: `TryStatement` поза дозволеними файлами;
- ESLint `no-restricted-imports`: драйвер БД лише в `repo-pg.js` і
  `platform/db`.

### Наслідки

- **Добре:**
  - шар порушення видно з імені файлу, а `make check` його ловить;
  - модуль лишається самодостатнім: моделі, помилки й SQL поруч;
  - глобальний обробник не залежить від класів модулів.
- **Погано / ціна:**
  - форма помилки — домовленість без спільного класу. Помилка без
    `statusCode` стане 500, тож тест має пройти кожен код каталогу;
  - модуль на 7 файлів навіть там, де логіки мало (`catalog`).

## Плюси й мінуси варіантів

### Варіант 2: папки-шари

- Плюс: шари видно з дерева.
- Мінус: модуль розпадається на чотири папки, межі модулів лаби 1 (К9:
  папка з однією точкою входу) зникають → відкинуто.

### Варіант 3: спільне ядро

- Плюс: один клас помилки, `instanceof` замість форми.
- Мінус: новий напрям залежностей — sf до правил 1–6 лаби 1; ядро швидко
  обростає чим завгодно → відкинуто.
