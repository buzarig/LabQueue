# ADR-0004: Історія здач — запит у модулі queue

- Статус: прийнято
- Дата: 2026-09-30
- Промпт: ai/lab1/008-architecture.md

## Контекст і проблема

Студент переглядає історію своїх здач (S13). Здача, що відбулася, — це
`QueueEntry` у кінцевому статусі «зараховано» чи «доопрацювання», з балом і
часом. Треба вирішити, чи виділяти історію в окремий модуль.

## Чинники рішення

- **Джерело правди — одне.** Результат здачі не повинен жити у двох місцях.
- **Межі модулів ведуть за володінням даними**, а не за екранами UI.
- **Жодних нових обходів `index.js`** і нових напрямів залежностей.

## Розглянуті варіанти

1. **Запит у `queue`.** Історія — функція читання над записами з результатом.
   Назву лаби й дату заняття вона бере через API `catalog` і `sessions`.
2. **Окремий модуль `history` з власною таблицею.** При фіксації результату
   `queue` копіює запис у `history`.
3. **Окремий модуль `history`, що читає дані `queue`.** Власних даних він не
   має.

## Рішення

Обрано **варіант 1**: історія — запит у `queue`.

### Наслідки

- **Добре:**
  - одне джерело правди;
  - історія не розходиться з чергою;
  - новий напрям залежностей не потрібен;
  - модулів менше — це відповідь на аудит «зайвих меж».
- **Погано / ціна:**
  - `queue` відповідає ще й за читання історії;
  - якщо історія зросте (звіти викладача, експорт, статистика), її варто
    буде виділити. Це буде новий ADR, що замінить цей.

## Плюси й мінуси варіантів

### Варіант 2: `history` з копією даних

- Плюс: історію можна оптимізувати під читання окремо від черги.
- Мінус: ті самі дані лежать у двох місцях. До того ж зміна результату чи
  помилка копіювання дає розбіжність. Для кількох записів на студента
  оптимізація не потрібна → відкинуто.

### Варіант 3: `history` читає дані `queue`

- Плюс: окрема папка для окремої функції.
- Мінус: модуль без власних даних або читає чужі таблиці (заборонено
  правилом 6 у «Напрямах залежностей»), або лише переказує API `queue`. Це
  межа без змісту, тобто саме те, що аудит шукає як зайве → відкинуто.
