# ADR-0026: Міграції — SQL-файли й власний ранер

- Статус: прийнято
- Дата: 2026-10-22
- Промпт: ai/lab2/013-vidpovid-idempotentnist-zboi-identychnist-mihratsii.md

## Контекст і проблема

Схему з `data.md` треба створити в локальній БД, у CI, у Supabase для демо,
а пізніше змінювати без ручних кроків. Повторний запуск не має нічого
ламати (spec лаби 2, К13).

## Чинники рішення

- **Видно, що виконується**: SQL з `data.md` 1:1 у файлах.
- **Кількість залежностей.**
- **Безпечність повторного й одночасного запуску** (CI, кілька терміналів).
- **Без ORM** ([ADR-0021](0021-postgresql-pg-i-sql.md)), тож міграцій з ORM
  немає.

## Розглянуті варіанти

1. **SQL-файли `migrations/NNN-назва.sql` і власний ранер
   `scripts/migrate.js`.**
2. **node-pg-migrate.**
3. **Один `schema.sql`**, що застосовується на старті, якщо таблиць немає.

## Рішення

Обрано **варіант 1** (промпт 013).
- Файли застосовуються в порядку імен. Кожен — у своїй транзакції.
- Весь запуск — під `pg_advisory_lock` з фіксованим ключем, тож два запуски
  не застосують одну міграцію двічі.
- Застосовані записуються в `public.schema_migrations (name, applied_at)`.
- Лише вперед, без down. Застосовану міграцію не змінюємо — лише нова.
- `make db-migrate`; `make check` застосовує міграції до тестової БД сам.

### Наслідки

- **Добре:**
  - нуль залежностей, ~50 рядків, які легко прочитати на захисті;
  - SQL у міграціях — той самий, що в `data.md`.
- **Погано / ціна:**
  - ранер — наш код, тож потрібен тест (повторний запуск нічого не
    змінює);
  - немає down-міграцій: відкат — нова міграція вперед;
  - змінену вже застосовану міграцію ранер не помітить. Контрольну суму не
    рахуємо — кандидат в аудит.

## Плюси й мінуси варіантів

### Варіант 2: node-pg-migrate

- Плюс: перевірений інструмент, блокування й журнал з коробки.
- Мінус: ще одна dev/prod-залежність, власний DSL або JS-міграції замість
  чистого SQL, а down-міграції нам не потрібні → відкинуто.

### Варіант 3: один `schema.sql`

- Плюс: найпростіше.
- Мінус: немає історії змін. Друга зміна схеми вимагала б ручного `alter`
  або перестворення БД → відкинуто.
