# ADR-0045: Blue-green — health check Railway на `/ready`

- Статус: прийнято
- Дата: 2026-11-24
- Промпт: ai/lab4/001-vymohy-laby-4.md

## Контекст і проблема

Вимога курсу: нова версія не отримує трафік, доки не готова; до того
працює стара. Spec лаби 4, критерій 6: Railway перемикає трафік після HTTP
200 від `/ready` нової версії з підключеною PostgreSQL. У застосунку два
технічні маршрути: `/health` — «процес живий», `/ready` — 200 лише коли
працює джерело даних, інакше 503
([ADR-0034](0034-fail-fast-i-zboi.md)).

## Чинники рішення

- **«Готова» означає, що відповідає й працює з БД.**
- **Без власного балансувальника**: перемикання робить платформа.

## Розглянуті варіанти

1. **Health check Railway на `/ready`.**
2. **Health check на `/health`.**
3. **Без health check**: трафік на новий контейнер одразу після старту.

## Рішення

Обрано **варіант 1**.

- Healthcheck Path сервісу Railway — `/ready`. Railway переводить трафік на
  новий деплой лише після 200 і до того лишає активним попередній.
- Healthcheck Timeout — типові 300 с: їх вистачає на seed перед HTTP.
  Фонові міграції ([ADR-0044](0044-mihratsii-u-chotyry-kroky.md)) його не
  затримують.
- Railway перевіряє з `healthcheck.railway.app` на порт зі змінної `PORT`,
  тож застосунок слухає `PORT` на всіх адресах
  ([ADR-0043](0043-dockerfile-i-sha-zbirky.md)).

### Наслідки

- **Добре:**
  - версія без з'єднання з БД трафік не отримує, стара працює далі;
  - логіку перемикання не пишемо самі.
- **Погано / ціна:**
  - Railway перевіряє health check лише під час деплою, а не постійно:
    падіння БД після перемикання він не помітить;
  - перемикання видно лише в журналі Railway; для доказу (критерій 6)
    потрібні HTTP-запити під час деплою.

## Уточнення (лаба 4, промпти 028, 029)

Рішення «health check Railway на `/ready`» не змінюється; змінено, що
означає «готова».

- **Що з'ясувалося:** перший деплой із `main` (`35b361f`) став активним і
  повернув правильний `/version`, але на кожен запит до API відповідав 500.
  У налаштуваннях сервісу не задали Pre-deploy Command і `SEED_ON_START`
  (автор, промпт 029), тож у БД не було схеми. `/ready` перевіряв лише `select 1` — з'єднання працювало, і
  Railway пустив трафік на зламану версію.
- **Як тепер:** `/ready` — 200, лише якщо в `public.schema_migrations`
  записано всі структурні міграції з теки `migrations/` поруч із
  застосунком (`src/../` або `dist/../`), той самий таймаут 1 с. Фонові
  дані й індекси (підтеки) `/ready` не чекає
  ([ADR-0044](0044-mihratsii-u-chotyry-kroky.md)).
- **Перевірка:** `tests/db/ready-schema.test.js`: без міграцій — 503, після —
  200, нова версія з незастосованою міграцією — 503. На старій перевірці
  два з трьох випадків падають.

## Плюси й мінуси варіантів

### Варіант 2: `/health`

- Плюс: відповідає найшвидше.
- Мінус: 200 навіть без БД — трафік піде на неготову версію → відкинуто
  (spec, критерій 6).

### Варіант 3: без health check

- Плюс: найшвидший деплой.
- Мінус: це не blue-green → відкинуто.
