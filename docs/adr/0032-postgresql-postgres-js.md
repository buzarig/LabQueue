# ADR-0032: PostgreSQL 17 і драйвер postgres.js з tagged templates; Supabase — лише демо

- Статус: прийнято
- Дата: 2026-10-23
- Промпт: ai/lab2/024-vidpovid-spec-zalezhnosti-seredovyshche-sql.md, ai/lab2/025-vidpovid-fail-fast-data-modeli-adr-0021.md

Замінює [ADR-0021](0021-postgresql-pg-i-sql.md): СУБД і роль Supabase
лишаються, драйвер і спосіб писати SQL змінюються.

## Контекст і проблема

Лаба 2 замінює статику реальною БД (промпти 003, 023). Від вибору залежать:
- захист I1–I4 під конкуренцією
  ([ADR-0022](0022-advisory-lock-za-vykladachem.md));
- видимість запитів для пошуку N+1;
- відтворення збоїв.

Курс рекомендує SQL tagged templates для сирого SQL (промпт 023). ADR-0021
обрав `pg` з параметрами `$1`, без тегів.

## Чинники рішення

- **Транзакції й блокування**: транзакції з кількох запитів, advisory lock,
  часткові унікальні індекси.
- **Видимий SQL** у tagged templates, параметри безпечні за побудовою.
- **Відтворюваність** без секретів автора.
- **Кількість залежностей і власного коду.**

## Розглянуті варіанти

1. **PostgreSQL + postgres.js (porsager/postgres).**
2. **PostgreSQL + `pg` + власний тег `sql`** (~30 рядків).
3. **PostgreSQL + Kysely або ORM** (Prisma, Drizzle).
4. **SQLite** (`node:sqlite`).

Доступ до Supabase: драйвер за рядком підключення або `supabase-js` (REST).

## Рішення

Обрано **варіант 1** (промпт 024). Цільова версія — PostgreSQL 17.
- **SQL** — tagged templates: `` sql`select … where id = ${id}` ``.
  Інтерполяція завжди стає параметром, тож SQL-ін'єкція неможлива за
  побудовою. Фрагменти й списки — через `sql(...)`; `sql.unsafe` заборонено
  лінтом.
- **Пул** — вбудований у postgres.js; `max: 10`, таймаути — [ADR-0034](0034-fail-fast-i-zboi.md).
- **Транзакції** — `sql.begin(tx => …)` всередині `unitOfWork`
  ([ADR-0030](0030-kontekst-zapytu-asynclocalstorage.md)).
- **Supabase** — лише хостинг PostgreSQL для ручного демо, через той самий
  postgres.js (session pooler); `supabase-js` не використовується.

### Наслідки

- **Добре:**
  - теги з коробки, без власного коду, який треба тестувати;
  - кожен запит сценарію видно в `repo-pg.js`;
  - одна prod-залежність без транзитивних.
- **Погано / ціна:**
  - postgres.js менш поширений за `pg`, менше прикладів;
  - його транзакції за замовчуванням передають `tx` параметром — ховаємо це
    в `unitOfWork` і контексті;
  - типи рядків пишемо JSDoc-ом у `model.js` ([ADR-0031](0031-rivni-dekompozytsii-i-modeli.md)).

## Плюси й мінуси варіантів

### Варіант 2: `pg` + власний тег

- Плюс: найпоширеніший драйвер, ADR-0021 не змінюється.
- Мінус: тег з фрагментами, списками й ідентифікаторами — наш код із
  власними тестами, тобто наш маленький драйвер → відкинуто.

### Варіант 3: Kysely або ORM

- Плюс: типи запитів зі схеми.
- Мінус: N+1 і блокування сховані за методами; з JSDoc перевага в типах
  слабшає → відкинуто (як в ADR-0021).

### Варіант 4: SQLite

- Мінус: немає advisory lock і `for update`, один записувач; збій
  «джерело недоступне» штучний → відкинуто (як в ADR-0021).

### `supabase-js`

- Мінус: REST не дає транзакції з кількох запитів, логіку довелося б
  перенести в SQL-функції → відкинуто (як в ADR-0021).
