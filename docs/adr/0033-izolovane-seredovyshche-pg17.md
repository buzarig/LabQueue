# ADR-0033: Ізольоване локальне середовище — власний кластер PostgreSQL 17 і БД на кожен прогін

- Статус: прийнято
- Дата: 2026-10-23
- Промпт: ai/lab2/023-dodatkovi-vymohy-laby-2.md, ai/lab2/024-vidpovid-spec-zalezhnosti-seredovyshche-sql.md

## Контекст і проблема

Курс рекомендує ізольоване локальне середовище: не 5432/5433/5434 на
localhost і окрема база на прогін чи гілку (промпт 023). Після sf-1 ми
працювали на спільному сервері EDB 18 на 5432 з однією `labqueue_test`:
- тести залежать від стану, який лишили інші прогони чи інші проєкти;
- версія 18 відрізняється від цільової 17 у CI і Supabase.

## Чинники рішення

- **Ізоляція**: власний порт, свої дані, БД на прогін.
- **Збіг версій** локально, у CI і Supabase.
- **Що треба встановити** автору й рев'юеру.
- **Одна команда** підняти й прибрати середовище.

## Розглянуті варіанти

1. **Власний кластер PG17 у репозиторії.** Бінарники `postgresql@17` з
   Homebrew (без служби); `make db-up` робить `initdb` у `.pgdata/` і
   запускає `pg_ctl` на `127.0.0.1:55432`.
2. **Docker/OrbStack** з `postgres:17` на нестандартному порту.
3. **Сервер EDB на 5432**, лише окрема БД на прогін.

## Рішення

Обрано **варіант 1** (промпт 024).
- **`make db-up`:**
  - створює кластер у `.pgdata/` (його ігнорує git), якщо його ще немає;
  - запускає сервер на `127.0.0.1:55432` і лише на unix-сокеті в
    `.pgdata/`;
  - створює роль `labqueue` і БД `labqueue_dev`.
- **`make db-down`** зупиняє сервер; **`make db-destroy`** видаляє
  `.pgdata/`.
- **БД на прогін.** Тестовий раннер створює `labqueue_t_<pid>_<час>` із
  шаблону `labqueue_tmpl`, де міграції вже застосовані, і видаляє її після
  прогону. Паралельні прогони й гілки не заважають одне одному.
- **Порт 55432** — поза 5432–5434, які курс радить не займати, і не
  перетинається з EDB на 5432.
- **CI** — service-контейнер `postgres:17`, ті самі змінні.
- Роль і БД на EDB 5432 із sf-1 більше не потрібні.

### Наслідки

- **Добре:**
  - локально, у CI і Supabase одна мажорна версія;
  - кожен прогін тестів на чистій БД, без ручного очищення;
  - нічого, крім `brew install postgresql@17`, ставити не треба; Docker
    не потрібен.
- **Погано / ціна:**
  - macOS + Homebrew — шлях до бінарників залежить від платформи; для
    Linux README дає ручний варіант;
  - кластер треба піднімати (`make db-up`) перед `make check`; без нього
    check зупиняється з підказкою;
  - sf-1 і розділ README «Середовище» переписуються.

## Плюси й мінуси варіантів

### Варіант 2: Docker/OrbStack

- Плюс: те саме середовище, що в CI, один `compose.yml`.
- Мінус: у автора Docker не встановлений; важка залежність для
  рев'юера заради одного процесу PostgreSQL → відкинуто.

### Варіант 3: EDB на 5432

- Плюс: уже працює, нічого не ставити.
- Мінус: прямо суперечить рекомендації курсу, спільний сервер з іншими
  проєктами, версія 18 замість 17 → відкинуто.
