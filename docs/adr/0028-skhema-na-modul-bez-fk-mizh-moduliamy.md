# ADR-0028: Схема PostgreSQL на модуль, зовнішні ключі лише всередині модуля

- Статус: прийнято
- Дата: 2026-10-22
- Промпт: ai/lab2/014-vidpovid-kliuch-pohodzhennia-spec.md, ai/lab2/015-adr-pyshemo-zaraz.md

## Контекст і проблема

У лабі 1 кожна сутність має одного власника, модуль читає чужі дані лише
через API, а між модулями ходять id (правило 6). Тепер ці межі мають
з'явитися в БД. Треба вирішити, де лежать таблиці й чи будуть зовнішні
ключі між таблицями різних модулів. Змінити це пізніше дорого: міграції
даних і переписування запитів.

## Чинники рішення

- **Межі модулів у даних** видно й можна перевірити.
- **Цілісність посилань.**
- **Свобода модуля** змінювати свої таблиці, не ламаючи чужі.
- **Простота** для одної БД і невеликого обсягу.

## Розглянуті варіанти

1. **Схема на модуль** (`identity`, `catalog`, `sessions`, `queue`,
   `platform`), FK лише всередині модуля.
2. **Одна схема `public`, FK між усіма таблицями.**
3. **Схема на модуль, FK і між модулями.**
4. **Окрема БД на модуль.**

## Рішення

Обрано **варіант 1**.
- Таблиці модуля — у його схемі. SQL модуля звертається лише до своєї схеми.
- Посилання на чужі дані — колонка з id і коментарем, звідки він, без FK.
- Цілісність перевіряє модуль-власник посилання через API при записі: S1
  питає `catalog`, S10 — `sessions`.

### Наслідки

- **Добре:**
  - правило 6 видно в SQL: ім'я схеми в запиті показує, чиї це дані.
    Можлива перевірка — grep чужих схем у `repo-pg.js` модуля;
  - модуль змінює свої таблиці без міграцій чужих;
  - видалення в одному модулі не каскадиться в інший.
- **Погано / ціна:**
  - БД не гарантує, що `queue.entries.lab_id` існує. Гарантує код, а сутності
    в MVP не видаляються;
  - join-ів між модулями немає. Дані з кількох модулів збираються
    пакетними запитами (`…ByIds`) — на один-два запити більше
    ([data.md](../specs/lab2-db-scenarios/data.md), «Запити сценаріїв»).

## Плюси й мінуси варіантів

### Варіант 2: одна схема з FK скрізь

- Плюс: цілісність гарантує БД, join-и доступні.
- Мінус: межі модулів у даних зникають, і join через чужу таблицю стає
  найпростішим шляхом. Правило 6 тримається лише дисципліною → відкинуто.

### Варіант 3: схеми з FK між модулями

- Плюс: цілісність і видимі межі.
- Мінус: модуль не може змінити свою таблицю, не зачепивши FK чужого. Seed
  і очищення в тестах мусять іти в порядку залежностей усіх модулів →
  відкинуто.

### Варіант 4: БД на модуль

- Плюс: повна ізоляція.
- Мінус: зникає транзакція на кілька модулів
  ([ADR-0023](0023-tranzaktsii-mizh-moduliamy.md)), а S4 і S10 її потребують.
  Для навчального MVP — надмір → відкинуто.
