# ADR-0035: Ідемпотентність — обов'язковий `Idempotency-Key`, запис у `unitOfWork`

- Статус: прийнято
- Дата: 2026-10-23
- Промпт: ai/lab2/014-vidpovid-kliuch-pohodzhennia-spec.md, ai/lab2/023-dodatkovi-vymohy-laby-2.md

Замінює [ADR-0024](0024-idempotency-key.md): правила ті самі, змінюється,
хто і що зберігає.

## Контекст і проблема

Повтори запитів (подвійний клік, таймаут, обрив на `COMMIT`) не мають
робити ще одну зміну. ADR-0024 зберігав HTTP-відповідь у транзакції, яку
відкривав рівень маршруту. Тепер транзакції живуть лише в шарі даних
([ADR-0030](0030-kontekst-zapytu-asynclocalstorage.md)), а роут не бачить
транзакцій. HTTP-відповідь формується вже після `COMMIT`.

## Чинники рішення

- **Повтор безпечний** для кожної змінювальної дії.
- **Атомарність** ключа й зміни.
- **Шари не змішуються**: роут не торкається транзакції, шар даних не
  знає HTTP.

## Розглянуті варіанти

1. **Ключ у контексті запиту; `unitOfWork` зберігає результат сервісу**
   (значення або код доменної помилки); роут однаково перетворює його на
   HTTP і для першого запиту, і для повтору.
2. **Зберігати HTTP-відповідь** у хуку `onSend` окремою транзакцією.
3. **Ідемпотентність у кожному сервісі** вручну.

## Рішення

Обрано **варіант 1**. Правила з ADR-0024 лишаються:
- `Idempotency-Key` обов'язковий на всіх POST (1–100 символів), без нього →
  400 `VALIDATION_FAILED`;
- область — (`user_id`, ключ), 24 години;
- той самий ключ з іншим методом, шляхом чи тілом → 409
  `IDEMPOTENCY_KEY_REUSED`;
- одночасні запити з одним ключем: другий чекає на унікальному індексі.

**Що змінюється:**
- Роут кладе ключ і хеш запиту (метод, шлях, тіло) у контекст запиту.
- `unitOfWork` на початку транзакції вставляє ключ. Якщо ключ уже є —
  повертає збережений результат без виклику сервісу.
- Сервіс виконується в savepoint. Його результат або доменна помилка
  (`code`, `statusCode`) записується в `platform.idempotency_keys.result`
  (`jsonb`) у тій самій транзакції. Доменна відмова відкочує лише savepoint.
- 5xx і тимчасові збої відкочують усе, тож повтор пробує знову.
- Роут перетворює результат на HTTP одним кодом для першого запиту й
  повтору. Збережена помилка проходить через той самий глобальний обробник.

### Наслідки

- **Добре:**
  - атомарність як в ADR-0024: зміна й ключ комітяться разом;
  - роут не бачить транзакцій, шар даних не бачить HTTP;
  - серверні ретраї ([ADR-0034](0034-fail-fast-i-zboi.md)) повторюють
    транзакцію разом з перевіркою ключа.
- **Погано / ціна:**
  - результат сервісу має бути серіалізовним у JSON (дати — рядки ISO);
  - кожен POST — ще 2 запити;
  - старі ключі лише ігноруються, таблиця росте — кандидат в аудит.

## Плюси й мінуси варіантів

### Варіант 2: відповідь в `onSend`

- Плюс: зберігається рівно те, що бачив клієнт.
- Мінус: окрема транзакція після `COMMIT` — між ними ключа немає, і повтор
  в цей момент зробить зміну вдруге; плюс транзакція на рівні HTTP →
  відкинуто.

### Варіант 3: у кожному сервісі

- Мінус: одна й та сама логіка в 11 командах, легко забути → відкинуто.
