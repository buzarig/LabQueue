# ADR-0021: PostgreSQL, драйвер `pg` і чистий SQL; Supabase — лише демо

- Статус: замінено ADR-0032
- Дата: 2026-10-22
- Промпт: ai/lab2/006-vidpovid-supabase-dostup.md, ai/lab2/015-adr-pyshemo-zaraz.md

## Контекст і проблема

Лаба 2 замінює статичні дані реальною БД (spec лаби 2, К7–К13). Треба обрати
СУБД і спосіб звертатися до неї з коду. Від вибору залежать:
- захист інваріантів I1–I4 під конкуренцією
  ([ADR-0002](0002-zakhyst-vid-honky-zapysiv.md));
- чи видно запити в коді: курс просить шукати N+1 (К12);
- як відтворити збої джерела (К11).

Автор запитав про Supabase (промпт 005).

## Чинники рішення

- **Транзакції й блокування**: транзакції з кількох запитів, блокування за
  довільним ключем, часткові унікальні індекси.
- **Видимість запитів**: кожен SQL видно в коді, тож N+1 і `for update`
  доводяться читанням коду й лічильником запитів.
- **Відтворюваність**: `make check` і CI на свіжому клоні без секретів автора.
- **Кількість залежностей** і сумісність із `checkJs`
  ([ADR-0007](0007-javascript-esm-jsdoc-checkjs.md)).

## Розглянуті варіанти

1. **PostgreSQL + `pg` + чистий SQL.**
2. **PostgreSQL + Kysely** (типізований query builder).
3. **PostgreSQL + ORM** (Prisma або Drizzle).
4. **SQLite** через вбудований `node:sqlite`.

Окремо — доступ до Supabase: через `pg` за рядком підключення або через
`supabase-js` (REST).

## Рішення

Обрано **варіант 1**: PostgreSQL 17, драйвер `pg` (`Pool`), SQL у файлах
репозиторіїв модулів. Типи рядків описуються JSDoc.

**Supabase** — лише хостинг PostgreSQL для ручного демо. Застосунок
підключається до нього тим самим `pg` через session pooler; `supabase-js` не
використовується. Тести й CI працюють на локальному PostgreSQL (`brew`,
service-контейнер `postgres:17`).

### Наслідки

- **Добре:**
  - є все потрібне: `pg_advisory_xact_lock`, часткові унікальні індекси,
    savepoint-и, SQLSTATE-коди для класифікації збоїв;
  - кожен запит сценарію записаний у `data.md` і видно в коді;
  - одна нова prod-залежність.
- **Погано / ціна:**
  - типи рядків пишемо вручну JSDoc-ом, і `tsc` не звіряє їх зі схемою;
  - `make check` потребує запущеного PostgreSQL (промпт 007);
  - мапінг snake_case → camelCase пишемо самі.

## Плюси й мінуси варіантів

### Варіант 2: Kysely

- Плюс: типи запитів виводяться з опису схеми.
- Мінус: ще одна залежність і шар, а перевага в типах слабшає з JSDoc замість
  TypeScript. Advisory lock і `any($1)` однаково пишуться через `sql\`…\``
  → відкинуто.

### Варіант 3: ORM

- Плюс: схема, міграції й типи з коробки.
- Мінус: запити сховані за методами моделей, тож N+1 і блокування
  доводяться лише логами. Prisma додає власний рушій і генерацію коду в
  збірку → відкинуто.

### Варіант 4: SQLite

- Плюс: вбудована в Node 24, без сервера й Docker.
- Мінус: один записувач на файл, немає `for update` і advisory lock, тож
  серіалізацію з ADR-0002 у БД не показати. Збій «джерело недоступне» для
  файлу в процесі штучний → відкинуто.

### `supabase-js` замість `pg`

- Плюс: не треба думати про пул і рядок підключення.
- Мінус: REST не дає транзакції з кількох запитів. Логіку черги довелося б
  перенести в SQL-функції (RPC), і інваріанти жили б у БД, а не в модулі
  `queue` (правило 7 лаби 1) → відкинуто.
