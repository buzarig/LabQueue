# ADR-0042: CD — Railway збирає коміт із `main` після зеленого CI

- Статус: прийнято
- Дата: 2026-11-24
- Промпт: ai/lab4/002-vidpovidi-zlyttia-hostyng-bd-tryger.md

## Контекст і проблема

Spec лаби 4 (критерії 3–4): коміт у `main` після зеленого CI автоматично
розгортається на staging. Раннер CI не має доступу до БД staging і не
заходить на машину по SSH. Треба обрати, хто запускає збірку й деплой.

## Чинники рішення

- **Деплоїться лише те, що пройшло CI.**
- **Жодних секретів staging у GitHub** і жодного SSH.
- **Простота**: один workflow `check.yml` уже є
  ([ADR-0015](0015-github-actions.md)).
- **Докази прогону** для аудиту (spec, критерій 14).

## Розглянуті варіанти

1. **Railway стежить за `main` і збирає сам** з увімкненим «Wait for CI».
2. **Actions збирає образ** після `make check`, пушить у GHCR і викликає
   deploy hook Railway.

## Рішення

Обрано **варіант 1** (рішення автора, промпт 002).

- Сервіс Railway підключений до репозиторію, гілка — `main`.
- «Wait for CI» увімкнено в налаштуваннях сервісу. За документацією
  Railway деплой чекає, доки завершаться всі workflow GitHub Actions на
  коміті, і пропускається, якщо хоч один упав. Умова — workflow з
  `on: push`; `check.yml` її виконує.
- Actions лишаються без змін: `make check` із власним PostgreSQL 17 у
  контейнері сервісу, без секретів staging.

### Наслідки

- **Добре:**
  - у GitHub немає жодного токена Railway; раннер CI не бачить ні БД, ні
    машини staging (критерій 3);
  - червоний `check` на коміті в `main` зупиняє деплой.
- **Погано / ціна:**
  - образ збирає Railway, а не CI: те, що пройшло `make check`, — той самий
    коміт, але інша збірка;
  - докази деплою — у журналі Railway, а не в Actions; для аудиту їх треба
    зберегти окремо (`reports/lab4/`);
  - «Wait for CI» — лише прапорець у панелі. За повідомленнями спільноти
    Railway він скидається після ручного «Redeploy»; перевіряємо його перед
    кожним доказом.

## Уточнення (лаба 4, промпти 040–062)

Рішення «Railway збирає з `main` після Wait for CI» не змінюється; змінено,
як його досягнуто, і `check.yml`.

- **Що з'ясувалося** (аудит, З4 і З6):
  - GitHub-застосунок Railway спершу не мав доступу до репозиторію: злиття
    PR #4–#6 не запускали деплой узагалі;
  - після надання доступу автодеплой працював, але прапорця «Wait for CI» не
    було, і деплой `bb693e6` випередив CI на `main`;
  - прапорець з'явився лише після того, як автор від'єднав і знову під'єднав
    репозиторій у Settings → Source; сервіс до того мав блок «Upstream Repo».
- **`check.yml`:** `push` — дослівно як у документації Railway: блоковий
  список лише з `- main`. Ціна: push у робочу гілку без PR не запускає CI —
  лише `pull_request` і pre-push локально. Яка зі змін `check.yml` (PR #8–#10)
  була потрібна, не з'ясовано; лишаємо дослівний варіант.
- **Доказ:** злиття PR #11 (`9d50a4a`): деплой у стані «WAITING FOR CI»,
  CI на `main` завершився о 23:17:54 UTC, нова версія — о 23:18:30, жодної
  відповіді `/ready`, крім 200; `reports/lab4/staging.txt` (CHK-25).
- **Що лишається вручну:** прапорець — налаштування панелі, не в git
  (ADR-0041); перед кожним доказом звіряти панель із README (MAN-11).

## Плюси й мінуси варіантів

### Варіант 2: образ з Actions → GHCR → deploy hook

- Плюс: деплоїться саме той образ, що пройшов CI; журнал Actions — доказ.
- Мінус: токен або hook Railway у секретах GitHub, окремий job і реєстр
  образів → автор обрав варіант 1.
