## Аудит CI: навмисні порушення (критерій 13)

Шість PR від `main` (#12–#17), у кожному одне порушення. Коміти зроблено й
запушено з `--no-verify`: локальні hook-и (pre-commit, commit-msg,
pre-push) такі зміни не пропустили б, а CI — остання лінія саме для цього
випадку.

| PR | Порушення | Де зупинився `make check` | Злиття |
|---|---|---|---|
| #12 | формат | `format` (Prettier) | BLOCKED |
| #13 | невикористана змінна | `lint` (ESLint `no-unused-vars`) | BLOCKED |
| #14 | `string` замість `number` у JSDoc | `typecheck` (TS2322) | BLOCKED |
| #15 | хибне очікування в тесті | `test` | BLOCKED |
| #16 | неіснуюча точка входу збірки | `build` (esbuild) | BLOCKED |
| #17 | `update readme wording` | `commits` (CHK-08) | BLOCKED |

Доказ — `reports/lab4/ci-violations.txt` (`make report-ci-violations`,
CHK-24): стан PR, висновок `check`, ціль make і рядки помилки з логу
GitHub Actions. Скрипт падає, якщо хоч один PR злитий, зелений або впав не
на очікуваній цілі. Злиття блокує ruleset `main` з обов'язковою перевіркою
`check` (`branch-protection.txt`). Після фінального `make verify` PR
закриваються без злиття.

## Журнал знахідок розгортання

### З1. Перший деплой старого `main` — без Dockerfile

- **Що:** підключений до `main` сервіс Railway одразу зібрав `9444816` (лаба
  2) автоматичним Railpack і впав на «Build image»
  ([020](../../ai/lab4/020-skrinshot-railpack-failed.md)).
- **Висновок:** очікувано, до БД цей деплой не дійшов. Після PR #4 збірка йде
  з `Dockerfile` (ADR-0043).

### З2. PostgreSQL 18 замість 17

- **Що:** стандартна БД Railway — PostgreSQL 18.7
  ([022](../../ai/lab4/022-server-version-18.md)), а критерій 4 і ADR-0033
  вимагають 17, як у CI.
- **Як виправлено:** БД без даних замінено шаблоном `postgres-17` —
  `17.12` ([024](../../ai/lab4/024-server-version-17.md)). Змінити тег образу
  на місці не можна: тека даних 18 для 17 нечитабельна.

### З3. Активна версія з 500 на кожен запит

- **Що:** перший активний деплой `35b361f` повертав правильний `/version` і
  `/ready` 200, але `GET /sessions` — 500 навіть для невідомого користувача.
  У сервісі не задали Pre-deploy Command і `SEED_ON_START`
  ([029](../../ai/lab4/029-zabuv-seed-predeploy-ready-v-pr2.md)) — у БД не
  було схеми.
- **Чому blue-green не захистив:** `/ready` перевіряв лише `select 1`.
  Відтворено локально: БД без міграцій — `/ready` 200, `/sessions` 500.
- **Як виправлено:** налаштування доповнено (Redeploy); `/ready` тепер 503,
  доки не застосовано всі структурні міграції (`3ed5ed3`, ADR-0045,
  «Уточнення», `tests/db/ready-schema.test.js`).

### З4. Злиття в `main` не запускають деплой

- **Що:** після злиття PR #4 (`35b361f`), PR #5 (`a36005b`) і PR #6
  (`fefb513`) CI на `main` зелений за ~35 с, але Railway не створив жодного
  деплою — навіть у стані «Waiting for CI»
  ([033](../../ai/lab4/033-skrinshot-deployments.md),
  [034](../../ai/lab4/034-ne-zyavyvsia-deploi.md),
  [039](../../ai/lab4/039-ne-bachu-waiting.md)).
- **Перша гіпотеза — хибна.** На кожному коміті `main` до PR #6 були набори
  перевірок застосунків **Render** і **Cursor** (`queued`, 0 запусків, в
  інтерфейсі GitHub не видно — лише `commits/<sha>/check-suites`). Я
  припустив, що «Wait for CI» чекає на них. Автор прибрав обидва застосунки
  ([036](../../ai/lab4/036-vydalyv.md)): на `fefb513` лишився тільки GitHub
  Actions, але деплою однаково не було.
- **Справжня причина:** у Settings → Source сервісу — «Auto deploy
  unavailable» і «Could not load branches»: GitHub-застосунок Railway не мав
  доступу до репозиторію ([040](../../ai/lab4/040-skrinshot-auto-deploy-unavailable.md)).
  Без нього Railway не отримує подій push, тож автодеплою не було з самого
  початку. Деплої `35b361f` в історії запустили зміни налаштувань і
  Redeploy, а не злиття.
- **Як виправлено:** автор надав Railway доступ до `LabQueue` і увімкнув
  автодеплой ([041](../../ai/lab4/041-pidkliuchyv-auto-deploy.md)).
  Доказ — злиття PR #7 (sf-2): деплой після зеленого CI.
- **Висновок для перевірки:** «зелений деплой» у панелі не доводить CD.
  Доказ автодеплою — новий коміт у `main`, після якого без жодних дій у
  панелі `/version` повертає його sha.

### З5. Порожній Healthcheck Path — 502 під час перемикання

- **Що:** злиття PR #7 (`bb693e6`, 22:27:41 UTC) уперше запустило
  автодеплой без дій у панелі. Спостерігач кожні 3 с: о 22:28:05 `/ready`
  дав **502**, о 22:28:09 — 200 на новій версії.
- **Причина:** поле Healthcheck Path сервісу було порожнє
  ([045](../../ai/lab4/045-healthcheck-pustyi.md)), тож Railway пустив
  трафік на контейнер одразу після старту, не чекаючи `/ready` — це
  порушує критерій 6 і ADR-0045.
- **Як виправлено:** автор задав `/ready`
  ([046](../../ai/lab4/046-hotui-healthcheck-dopysav.md)).
  Лог збірки деплою `7881dac` (експорт автора,
  [052](../../ai/lab4/052-lohy-ostannoho-deploiu.md)), UTC:

  ```
  22:38:39 ==================== Starting Healthcheck ====================
  22:38:39 Path: /ready
  22:38:39 Retry window: 5m0s
  22:38:42 [1/1] Healthcheck succeeded!
  ```

  Спостерігач щосекунди: перемикання PR #8 — 26 запитів `/ready`, PR #11 —
  53, жодного не 200.

### З6. Деплой раніше за CI — немає «Wait for CI»

- **Що:** той самий деплой `bb693e6` обслуговував запити о 22:28:05, а CI
  на `main` завершився о 22:28:20. Railway одразу показав зелений статус,
  етапу «Waiting for CI» не було
  ([044](../../ai/lab4/044-odrazu-zelenyi-bez-wait.md)): прапорця в
  налаштуваннях немає. Якби CI на `main` упав, коміт однаково потрапив би
  на staging — критерій 4 не виконано.
- **Що зроблено:** `check.yml` отримав `push: branches: ["**"]` — за
  документацією Railway прапорець з'являється лише для workflow з `on: push`
  і переліком гілок. Після злиття (PR #8) прапорця однаково немає
  ([050](../../ai/lab4/050-skrinshot-source-bez-wait.md)); конфіг-файл
  Railway поля `checkSuites` не має (схема `railway.schema.json`). Друга
  спроба — `branches: [main, "**"]` (PR #9); третя — дослівно як у
  документації: блоковий список лише з `- main` (PR #10). Ціна третьої:
  push у робочу гілку без PR більше не запускає CI — лише `pull_request` і
  pre-push локально ([060](../../ai/lab4/060-tochno-yak-railway.md)).
- **Хронологія PR #8** (`7881dac`): автодеплой обслуговує запити о 22:37:10,
  CI на `main` завершився о 22:37:30. Другий деплой того самого коміту о
  22:38:26 (збірка повністю з кешу, Healthcheck `/ready` — succeeded) запустив
  автор оновленням репозиторію в панелі
  ([054](../../ai/lab4/054-onovyv-repo-v-railway.md)), не злиття.

- **Як з'явився прапорець:** після PR #10 автор від'єднав репозиторій від
  сервісу й під'єднав знову — прапорець «Wait for CI» з'явився, автор його
  увімкнув ([061](../../ai/lab4/061-perepidkliuchyv-wait-for-ci.md)). Сервіс
  мав блок «Upstream Repo» з кнопкою «Eject» — схоже, створений із
  шаблону; після перепідключення налаштування джерела оновились. Яка з
  трьох змін `check.yml` була потрібна, не з'ясовано: лишаємо дослівний
  варіант документації. Доказ — злиття PR #11: деплой у стані «Waiting for
  CI» до зеленого CI.

### Спільний висновок З3, З5, З6

Усі три — розбіжність панелі Railway з таблицею README «Staging», яку мала
ловити рев'ю MAN-11. Налаштування в панелі не в git і не перевіряються
автоматично (ціна в ADR-0041), тож перед кожним доказом панель треба
звіряти з таблицею вручну.

## Кандидати «зрізаних кутів» ШІ

1. **`SHOW server_version` без `psql`.** Я дав SQL-команду, не сказавши, що
   її виконують у `psql`; автор запустив її в bash
   ([021](../../ai/lab4/021-show-server-version-ne-pratsiuie.md)).
2. **Злиття без перевірки наборів перевірок коміту.** Перед злиттям PR #4 я
   перевірив лише `gh pr checks`, який показує тільки набори з запусками, і
   не подивився `check-suites` — завислі Render і Cursor знайшлись лише
   після двох злиттів без автодеплою.
3. **Затримку пояснено без перевірки.** Деплой PR #4 з'явився через ~14 хв
   після злиття; я пояснив це повільною реакцією Railway на CI, не
   з'ясувавши, чим насправді його запущено (З4).
4. **Висновок про причину без перевірки налаштувань.** У З4 я спершу
   звинуватив Render і Cursor за повідомленнями спільноти, хоча
   найпростішу причину — чи підключено автодеплой у Settings → Source —
   можна було перевірити першою. Через це знадобився зайвий PR #6.
